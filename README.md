# QFabric

**Hardware-agnostic control and calibration fabric for heterogeneous quantum hardware.**

> **Status:** pre-alpha / experimental. QFabric v0.7 defines a vendor-neutral,
> versioned control protocol, a pinned plan-only QICK backend profile, an upstream
> API drift harness, and a controlled QICK runtime-binding fixture. It does **not**
> claim physical-hardware compatibility unless a future executor and hardware-specific
> integration are explicitly tested.

QFabric explores a thin public control layer between higher-level quantum software
and heterogeneous hardware backends. The public core makes protocol versions,
control commands, capabilities, calibration provenance, backend mappings, and failure
modes explicit without coupling the core package to one vendor SDK.

## Why QFabric?

Quantum hardware stacks expose different control surfaces, calibration concepts,
and telemetry formats. QFabric asks:

> What is the smallest useful protocol that can sit above multiple hardware families
> without pretending their underlying physics is identical?

v0.3 added one more question:

> Can that protocol be mapped deterministically onto a real, public quantum-control
> API without silently importing its runtime or pretending hardware was exercised?

The first answer is the **QICK plan profile**, pinned to upstream commit
`4da51a5154e448fa3613257a967bfa6a58959a8b`.

v0.4 adds a second:

> Can QFabric detect when an upstream backend API changes in a way that invalidates
> the pinned mapping?

The QICK drift harness answers this by comparing the latest upstream API surface
against a machine-readable contract for the methods QFabric actually depends on.

v0.5 adds a third question:

> Does a real, pinned QICK Python runtime actually accept the keyword-call shapes
> generated by QFabric?

The controlled runtime fixture installs QICK at the pinned reference commit, imports
the real QICK classes, and binds each generated plan call with `inspect.signature`.
It never instantiates a QICK program, connects to an RFSoC, or executes a pulse.

## Quick start

Requires Python 3.11+.

~~~bash
git clone https://github.com/Takzin1/QFabric.git
cd QFabric
python -m pip install -e ".[dev]"
pytest
~~~

### QICK plan example

~~~python
from datetime import UTC, datetime

from qfabric.models import ControlCommand, ExperimentRequest
from qfabric.profiles.qick import QickGeneratorBinding, QickPlanAdapter
from qfabric.protocol import CommandEnvelope

adapter = QickPlanAdapter(
    device_id="qick-lab-01",
    bindings=(
        QickGeneratorBinding(logical_channel="drive", gen_ch=0, nqz=1),
    ),
)

envelope = CommandEnvelope(
    message_id="msg-001",
    device_id="qick-lab-01",
    sent_at=datetime.now(UTC),
    request=ExperimentRequest(
        commands=(
            ControlCommand(
                channel="drive",
                value=0.5,
                unit="normalized_gain",
                duration_s=1e-6,
                metadata={
                    "qick.frequency_mhz": 100.0,
                    "qick.phase_deg": 0.0,
                    "qick.time_us": 0.0,
                },
            ),
        )
    ),
)

plan = adapter.compile(envelope)

for call in plan.calls:
    print(call.method, dict(call.kwargs))
~~~

This produces a reviewable QICK-shaped plan. It does **not** dispatch the plan to a
QICK program or RFSoC.

## Core invariants

1. The core package does not import vendor SDKs.
2. Hardware-specific behavior lives behind explicit adapter/profile boundaries.
3. Cross-boundary commands carry an explicit protocol version and target device.
4. Capabilities are negotiated explicitly rather than silently degraded.
5. Calibration records are versioned, timestamped, and carry provenance.
6. Unsupported channels and device mismatches fail closed with stable error codes.
7. Generic conformance inspection never executes hardware commands.
8. Backend profiles pin the upstream source they were verified against.
9. Plan generation and physical execution remain separate.
10. Hardware compatibility claims require hardware-specific documentation and tests.
11. Upstream compatibility is checked by API surface, not by commit SHA alone.
12. Backend API drift must fail visibly before QFabric silently assumes compatibility.
13. Source-shape compatibility and imported-runtime compatibility are separate checks.
14. Runtime compatibility checks MUST bind calls without constructing hardware objects.
15. Plan compilation rejects non-finite pulse parameters, conversion overflow, and
    overlapping pulses on a shared QICK generator before exposing the plan.

## NVIDIA / CrystalTwinAI offline research bridge (experimental)

See [design, contracts, and safety boundaries](docs/integrations/crystaltwin-nvidia.md).
CrystalTwinAI exports a synthetic educational snapshot; QFabric validates it,
builds a QICK **plan only**, performs CPU or optional real CuPy/CUDA synthetic
IQ analytics, and produces a locally importable research report. No quantum
readout, crystallization measurement, quantum advantage or physical control
is claimed.

~~~bash
python scripts/crystaltwin_bridge.py snapshot.json report.json --backend cpu --shots 4096
~~~

This cross-repo research demonstrator is independent of the QFabric core
protocol and vendor-SDK-free planning guarantees.

### v0.6 — QICK readout intent and evidence verification

- [x] QICK-specific `QickReadoutIntent` with finite numeric bounds and explicit ADC/generator allowlists
- [x] Keep readout non-executing; return serializable intent, never acquisition methods
- [x] Include readout intent in offline CrystalTwinAI report without breaking v1 import
- [x] Verify exact source snapshot SHA-256, demo plan, synthetic labels and result invariants
- [x] Mirror a bounded CrystalTwinAI synthetic fixture and exercise CLI generate/verify in CI
- [ ] Map pinned QICK readout API methods only after upstream source/runtime semantic audit
- [ ] Benchmark optional NVIDIA CUDA path on verified GPU hardware

Read [QICK readout design and safety limits](docs/adapters/qick-readout-intent.md).
After exporting a CrystalTwinAI snapshot:

~~~bash
python scripts/crystaltwin_bridge.py snapshot.json report.json --backend cpu --shots 256
python scripts/crystaltwin_bridge.py snapshot.json report.json --verify
~~~

`--verify` validates consistency against the supplied exact input bytes, not
cryptographic authorship, measured data or GPU use.

### v0.7 — Experiment Orchestration Layer (offline)

**Implemented:** model-neutral, untrusted research-proposal schema, hash-bound
CrystalTwinAI input, strict educational parameter guards, rejection reasons
and a self-attested human-review boundary. **Not implemented:** Nebius/NVIDIA
model inference, automated physical control or authenticated approvals.

~~~bash
python scripts/research_agent_gate.py prepare tests/fixtures/crystaltwin_snapshot.synthetic.json proposal.json --parameter coolingRate --value 0.25
python scripts/research_agent_gate.py assess tests/fixtures/crystaltwin_snapshot.synthetic.json proposal.json assessment.json
python scripts/research_agent_gate.py review tests/fixtures/crystaltwin_snapshot.synthetic.json proposal.json assessment.json review.json --reviewer-label demo-human --decision approve --attest-educational-only
~~~

The prepare command generates an explicitly **synthetic fixture**; it does not
pretend to contact Nemotron. See the
[Experiment Orchestration specification](docs/integrations/experiment-orchestration.md).

## Quantum research datasets — source catalog (documentation)

The [quantum research dataset catalog](docs/datasets/quantum-research-dataset-catalog.md)
lists four paper-linked sources for future QFabric evidence ingestion: measured
superconducting-qubit/QEC datasets and a separately labelled **simulation-only**
benchmark. Each entry includes primary paper/data URLs, priority, expected file
formats, estimated size, NotebookLM/Gemini Notebook extraction instructions,
license/units verification status, and safe ingestion gates.

**Documentation only:** no third-party raw dataset has been downloaded,
rehosted, validated or used to demonstrate real quantum hardware compatibility.
Notebook-derived summaries are not a replacement for original data files.

## Open-core boundary

QFabric publishes the reusable protocol, SDK boundary, schemas, planning profiles,
and adapter contract.

Physics-accurate digital twins, proprietary inference engines, private training data,
and commercial evaluation services are intentionally outside this repository.
